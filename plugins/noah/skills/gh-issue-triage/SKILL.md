# GH Issue Triage

以八維度分析框架評估 GitHub Issue 是否適合由 `gh-issue-opsx-autopilot` 自動化處理，輸出結構化檢核報告。

**輸入**：`$ARGUMENTS` = GitHub Issue 編號（如 `100`）

---

## 執行流程

### Step 1：讀取 GH Issue

```bash
gh issue view $ARGUMENTS --json title,body,assignees,labels,comments,author
```

提取 title、body、labels、comments、assignees、author。

**需求來源優先順序**：Issue body 為原始需求，comments 為補充與定案。若 body 與 comments 有衝突，以 comments 為準。

**既有分析去重**：檢查 comments 中是否已有 triage 報告或技術分析。若已有：
- 驗證其結論在當前程式碼狀態下是否仍成立
- 若前次 triage 為舊版（五維度），在驗證基礎上補充分析新維度（D2～D6 中前次未涵蓋者）
- 產出完整八維度報告，標注哪些維度為「沿用前次結論（已驗證）」

若 Issue 帶有 `discussion` 標籤，**立即中止**並回報：
> Issue #$ARGUMENTS 標記為 `discussion`，尚待團隊討論，不適合進入自動化流程。

### Step 2：查閱既有規格文件與程式碼

依文件層級由下游往上游查找，以最接近實作的規格為準：

1. 先查 `openspec/specs/` 是否有對應的技術規格
2. 若無，查 `sa/spec/` 是否有對應的系統分析規格
3. 若皆無，表示此 Issue 為全新需求，尚無既有規格可參照

同時讀取現有程式碼中與 Issue 相關的檔案，建立對現狀的理解。

### Step 3：變更特徵分析與深度判定

根據 Step 1、Step 2 取得的資訊，依序完成以下三個子步驟。

#### 3.1 識別變更特徵

分析 Issue 實際涉及的變更特徵，標注適用的標籤（可複選）：

| 變更特徵標籤 | 判定依據 |
|-------------|---------|
| `user-facing` | 涉及使用者可見的行為、UI、操作流程、權限變更 |
| `data-model` | 涉及 Entity/Table/Schema 新增或修改、資料驗證規則、持久化邏輯 |
| `interface` | 涉及 API 端點、CLI 參數、Public API、前後端互動介面的新增或變更 |
| `stateful` | 涉及物件狀態轉移、工作流程、審批流程、排程、非同步處理 |

**不確定時預設適用**：若無法確定某標籤是否成立，視為適用（寧可多檢核，不可遺漏）。

#### 3.2 決定維度適用性

| 維度 | 類型 | 適用規則 |
|------|------|---------|
| D1 需求釐清 | 恆適用 | — |
| D2 使用者情境 | 條件適用 | 具有 `user-facing` 標籤時適用 |
| D3 資料模型 | 條件適用 | 具有 `data-model` 標籤時適用 |
| D4 介面契約 | 條件適用 | 具有 `interface` 標籤時適用 |
| D5 狀態與流程 | 條件適用 | 具有 `stateful` 標籤時適用 |
| D6 非功能需求 | 恆適用 | — |
| D7 影響分析 | 恆適用 | — |
| D8 可實作性驗證 | 恆適用 | — |

#### 3.3 判定分析深度

| 深度 | 判定條件 | 每維度產出量 |
|------|---------|------------|
| **輕量** | 單檔變更、設定調整、文案修正、typo 修正 | 一句話評估 |
| **標準** | 單模組範圍、一般 feature 或 bugfix | 一段落分析（3-5 句） |
| **深入** | 跨模組變更、架構層級異動、資料模型大幅修改、高風險變更 | 完整子章節含技術細節 |

判定規則：
- 若 Step 2 發現涉及 ≥2 個獨立模組 → **深入**
- 若變更特徵標籤 ≤1 個且影響單一檔案或目錄 → **輕量**
- 其餘 → **標準**

#### 3.4 常見情境參考矩陣

此矩陣為快速參照，**不具強制力**，最終適用性由 3.2 的規則決定。若判定結果與矩陣嚴重偏離，應重新審視變更特徵標籤是否正確。

| 常見情境 | 典型標籤組合 | 通常適用維度 |
|---------|------------|------------|
| Web App 功能 | `user-facing` + `data-model` + `interface` + `stateful` | D1～D8 全適用 |
| API 端點 | `data-model` + `interface` | D1, D3, D4, D6, D7, D8 |
| 背景計算/排程 | `data-model` + `stateful` | D1, D3, D5, D6, D7, D8 |
| CLI 工具 | `interface` | D1, D4, D6, D7, D8 |
| Library/SDK | `interface` | D1, D4, D6, D7, D8 |
| 設定/環境變更 | （無標籤） | D1, D6, D7, D8 |
| 資料遷移 | `data-model` + `stateful` | D1, D3, D5, D6, D7, D8 |
| Bug Fix | 視 bug 性質 | D1, D6, D7, D8 + 視情況 |
| 文案/UI 調整 | `user-facing` | D1, D2, D6, D7, D8 |

### Step 4：八維度檢核

根據 Step 1～3 取得的資訊，對每個**適用**維度執行檢核。跳過的維度記錄跳過原因。

---

#### D1 需求釐清（What）— 恆適用

檢核項：

- **範圍界定**：Scope（做什麼）與 Out of Scope（不做什麼）是否可從 Issue 中辨識
- **驗收條件**：能否從 Issue 提煉出具體的 Acceptance Criteria（怎樣算「做完了」）
- **一致性**：Issue body 與 comments 之間有無矛盾或多種合理解讀
- **充分性**：描述是否完整到可直接轉化為 spec，無需回頭詢問

---

#### D2 使用者情境（Who & How）— 條件適用

**適用條件**：Issue 涉及使用者可見的行為變更（UI 互動、操作流程、權限控制）
**跳過條件**：純後端邏輯、背景計算、資料遷移、設定變更等無使用者直接互動的變更

檢核項：

- **角色識別**：涉及哪些使用者角色（Actor），各角色的操作權限是否明確
- **主要流程**：Happy Path 是否可從 Issue 中描述，步驟是否清晰
- **例外流程**：Edge Cases 是否已考量（輸入錯誤、權限不足、並行操作等）
- **權限模型**：各角色可見與可操作的範圍是否定義

---

#### D3 資料模型（Data）— 條件適用

**適用條件**：Issue 涉及 Entity/Table/Schema 新增或修改、資料驗證規則變更、持久化邏輯
**跳過條件**：不涉及資料結構或持久化變更（如純 UI 調整、CLI 參數變更、設定檔修改）

檢核項：

- **Entity 設計**：需要新增或修改哪些 Entity，欄位與型別是否可從 Issue 推知
- **關聯關係**：Entity 之間的 1:1 / 1:N / M:N 關係是否清楚
- **資料驗證**：必填、格式、範圍、唯一性等約束是否定義
- **資料生命週期**：建立、更新、刪除、歸檔的規則是否考量

---

#### D4 介面契約（Interface）— 條件適用

**適用條件**：Issue 涉及 API 端點、CLI 參數/子命令、Public API 簽名、前後端互動介面的新增或變更
**跳過條件**：不涉及任何介面邊界變更（如內部重構、背景排程邏輯、資料遷移）

檢核項：

- **介面定義**：API 端點 / CLI 參數 / Public API 簽名是否明確（或可從 Issue 推導）
- **輸入輸出**：Request/Response 結構或輸入/輸出格式是否可辨識
- **錯誤處理**：錯誤回應或異常情境的處理方式是否規範
- **相容性**：是否為既有介面的變更（需考量向後相容），或全新介面

---

#### D5 狀態與流程（State & Flow）— 條件適用

**適用條件**：Issue 涉及物件狀態轉移、工作流程、審批流程、排程觸發、非同步處理
**跳過條件**：無狀態操作（如 CRUD 無流程控制、靜態頁面、設定變更）

檢核項：

- **狀態識別**：核心物件有哪些狀態，是否可列舉（如：草稿 → 審核中 → 已核准）
- **轉移條件**：每個狀態轉移的觸發條件與前置條件是否定義
- **併發處理**：同時操作時的衝突處理策略是否考量
- **回滾機制**：失敗時是否需要回滾，回滾策略是否明確

---

#### D6 非功能需求（NFR）— 恆適用

檢核項：

- **效能**：是否有回應時間、吞吐量、資料量級等效能影響需考量
- **安全性**：是否涉及認證、授權、資料加密、輸入驗證、稽核日誌等安全面向
- **可用性**：是否需要錯誤處理策略、降級方案、重試機制

輕量深度時，若明顯無 NFR 顧慮（如 typo 修正），以「無特殊非功能需求」一句話帶過即可。

---

#### D7 影響分析（Impact）— 恆適用

檢核項：

- **問題存續性**：檢查最新程式碼與近期 commit 歷史（`git log --oneline -30`），確認問題未被其他 PR 或 commit 修復。若問題已不存在，說明是哪個 commit 或 PR 解決的
- **變更範圍**：涉及哪些檔案與模組，是否跨模組（跨模組修改風險較高），預估變更量級（小 / 中 / 大）
- **既有功能衝突**：新需求是否與現有行為矛盾
- **資料遷移**：是否需要 migration，既有資料如何處理
- **向後相容**：API 或行為變更是否影響既有使用者或下游系統

---

#### D8 可實作性驗證（Feasibility）— 恆適用

檢核項：

- **技術可行性**：現有技術棧是否支撐，有無需要引入新依賴或框架
- **可拆分性**：能否拆為獨立、可逐步交付的工作單元
- **可測試性**：每個工作單元是否有明確的測試策略
- **依賴排序**：工作單元之間的先後順序與相依關係
- **Autopilot 適配性**：綜合以上各維度，判斷是否適合自動化處理
  - 需求邊界清晰（D1 無重大疑慮）
  - 不涉及架構大改或底層框架變更
  - 影響範圍可控（D7 無跨模組高風險）
  - 不需要與外部系統整合或人工介入決策
- **前置作業**：有無相依 Issue 未完成（檢查 Issue body 與 comments 中的引用）、是否與其他進行中的 feature branch 衝突（`git branch -r --list 'origin/feature/*'`）、有無需要先行處理的技術債或前置條件

### Step 5：輸出結論

根據八維度檢核結果，給出總結論與結構化報告。

---

```markdown

- **特徵標籤**：`user-facing`, `data-model`（或「無條件標籤」表示僅觸發恆適用維度）
- **分析深度**：輕量 / 標準 / 深入
- **適用維度**：D1, D2, D3, D6, D7, D8
- **跳過維度**：D4（不涉及介面變更）、D5（無狀態流程）
```

### 結論推導規則

| 條件 | 總結論 |
|------|--------|
| 所有**適用**維度皆 ✅ | ✅ 可直接執行 |
| 任一適用維度 ❌ | ❌ 不建議自動化 |
| 其餘（有 ⚠️ 但無 ❌） | ⚠️ 建議先處理以下事項 |

- 跳過（✘）的維度**不參與**結論判定
- D8 的「Autopilot 適配性」子項為最終綜合判斷，若其他維度皆 ✅ 但此子項為 ❌，總結論仍為 ❌

### 結論三分法

| 結論 | 含義 | 建議動作 |
|------|------|---------|
| ✅ 可直接執行 | 所有適用維度皆無阻礙 | 執行 `/noah:gh-issue-opsx-autopilot $ARGUMENTS` |
| ⚠️ 建議先處理 | 有可排除的障礙 | 處理完障礙後再執行 autopilot |
| ❌ 不建議自動化 | 存在根本性障礙 | 需人工介入處理或重新定義需求 |

## Guardrails

- 此 skill 為**純分析型**，不建立分支、不修改程式碼、不留言 Issue
- 所有判斷須基於實際程式碼與 Issue 內容，不做臆測
- 輸出使用繁體中文
