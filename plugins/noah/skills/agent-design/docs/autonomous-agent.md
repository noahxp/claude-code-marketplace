# Autonomous Agent 知識庫

## 這個架構適用的場景

這是為**任務複雜、無法預先規劃所有路線**的 Agent 設計的架構。

核心設計思路是：不預先定義流程，而是給 AI 一個大的 system prompt 加上一組工具定義，讓 AI 自己判斷每一步該做什麼、該用什麼工具。流程由 AI 動態決定，不是開發者寫死的。

**與其他類型的差異：**

- 跟**簡單型**的差異：簡單型是固定管線（用戶輸入 → 撈資料 → 組裝 → 回應），每次走一樣的路。自主型沒有固定路線，AI 自己決定要不要撈資料、要用哪個工具、要跑幾步。
- 跟**分流型**的差異：分流型用意圖分析當路由器，預先定義好幾條路線讓 AI 選。自主型不需要意圖分析，因為 AI 透過選擇工具來隱式表達它理解的意圖——選了什麼工具，就等於判斷了用戶的意圖。

自主型的特點是：**靈活度最高、能處理開放式任務、但成本較高且需要更多外部管控機制**。適合任務範圍廣、步驟無法預測的場景。

## 基礎 Part 1 — Agent 架構與流程

整個 Agent 的運作是一個 **while 迴圈**：

```
用戶輸入
  ↓
┌─────────────────────────────┐
│  組裝上下文（system prompt  │
│  + 對話紀錄 + 工具定義）     │
│         ↓                   │
│  Call AI API                │
│         ↓                   │
│  AI 回應（文字 或 工具呼叫） │
│         ↓                   │
│  有工具呼叫？               │
│   ├─ 有 → 執行工具 → 把結果 │
│   │       送回 AI → 回到頂部 │
│   └─ 沒有 → 結束，回應用戶  │
└─────────────────────────────┘
```

### 1. 組裝上下文

每一輪都要重新組裝一包資訊送給 AI。AI 不會自己記住上一輪發生了什麼，你給什麼它就看什麼。

這包資訊包含：
- **System Prompt**：AI 的角色設定、行為規範、工具使用規則
- **工具定義**：有哪些工具可以用、每個工具的參數格式
- **對話紀錄**：到目前為止的所有對話（包含之前的工具呼叫和結果）
- **用戶訊息**：用戶這次說的話

### 2. Call AI API

把組裝好的上下文送給 AI。AI 會回傳兩種東西的其中一種：

- **純文字回應**：AI 覺得可以直接回答了
- **工具呼叫（tool_use）**：AI 覺得需要先用某個工具取得資訊或執行某個動作

### 3. 工具執行

如果 AI 回傳了工具呼叫，系統就執行對應的工具（例如查資料庫、讀檔案、搜尋網路），把結果包成 tool_result 送回給 AI。

AI 拿到結果後可能會：
- 直接根據結果回答用戶
- 再呼叫另一個工具（例如查完資料庫後再搜尋網路補充）
- 繼續多步驟操作

### 4. 迴圈結束

當 AI 回傳的是純文字（沒有工具呼叫）時，迴圈結束，把回應送給用戶。

**關鍵概念：** 整個流程裡，「要不要用工具」、「用哪個工具」、「用完要不要再用另一個」——全部是 AI 自己決定的。開發者只定義了有哪些工具可以用，不規定什麼時候該用。

## 進階 Part 2 — 模組知識庫

> 以下是各模組的進階知識點，按需查閱。

### Tool Use（工具使用）

- **工具定義的結構**：每個工具需要定義三個東西——名稱（name）、功能說明（description）、參數格式（parameters，用 JSON Schema 描述）。AI 根據 description 判斷什麼時候該用這個工具，根據 parameters 知道要帶什麼參數。
- **description 決定觸發時機**：description 寫得好不好，直接決定 AI 會不會在對的時機選這個工具。太模糊會亂選，太狹窄會漏選。要寫清楚「這個工具做什麼」和「什麼情境下該用」。
- **工具選擇 = 隱式意圖分析**：AI 選了什麼工具，就等於它判斷了用戶的意圖。不需要另外寫一個意圖分類器，行為規則寫在 system prompt 裡就夠了。
- **工具結果的格式**：工具執行完，結果要以結構化的方式回傳給 AI。跟上下文工程一樣的原則——結構化文字比 raw data 好，要告訴 AI 這是什麼資料、怎麼用。
- **工具的權限控制**：不是所有工具都該讓 AI 隨便用。危險操作（刪除、發送、修改）要在執行前加一層檢查，確認是否安全或需要用戶確認。

### System Prompt 設計

自主型 Agent 的 system prompt 是整個系統最重要的部分，因為 AI 的所有行為都由這份 prompt 控制。

- **基本結構**：建議分成以下區塊，按順序排列：

  1. **角色定義** — 你是誰、你的職責是什麼
  2. **行為規範** — 該做什麼（Dos）、不該做什麼（Don'ts）
  3. **工具使用規則** — 什麼時候該用什麼工具、使用限制、優先順序
  4. **輸出規範** — 回應格式、語氣、長度
  5. **動態資訊** — 當前狀態、環境資訊等每次可能不同的內容

- **行為規則取代分類器**：不需要寫意圖分類邏輯，改成在 prompt 裡寫非常具體的行為規則。例如：「當用戶問到 X 時，先用 A 工具查，查不到再用 B 工具」。規則寫得越具體，AI 的行為越可預測。

- **靜態與動態分離**：prompt 裡有些內容每次都一樣（角色設定、行為規範），有些每次不同（當前狀態、環境資訊）。把固定的放前面、會變的放後面，可以利用 API 的 prompt caching 功能降低成本——前面固定的部分只需要處理一次，之後都命中快取。

- **prompt caching 的概念**：大部分 AI API 都支援 prompt caching。原理是：如果你送的 prompt 前半段跟上次一模一樣，API 可以跳過重新處理，直接從不一樣的地方開始。對話越長、prompt 越大，省的錢越多。關鍵是「固定內容放前面、會變的放後面」。

### AI 的弱項與對策

自主型 Agent 把流程控制權交給 AI，所以 AI 做不好的事情全部會浮現。以下是需要用程式碼強制管控的弱項：

#### 上下文管理

**弱項：** AI 不會主動管理自己的 context。對話越長，context 越大，直到撞上限制。

**對策：**
- **自動壓縮**：設定 token 門檻，快到上限時自動把舊對話摘要成精簡版本
- **訊息修剪**：自動移除太舊的訊息，只保留最近的對話
- **工具結果截斷**：工具回傳的結果太大時，自動截斷到合理大小，不讓整個檔案塞進 context
- **多階段降級**：快爆了先壓縮文字 → 還是太大就移除圖片 → 還是不行就只保留摘要。逐步降級，不是一次砍光

#### 成本控制

**弱項：** AI 不知道每次 API call 花了多少錢，也不會自己省錢。

**對策：**
- **費用追蹤**：每次 API call 後自動計算 token 用量和費用，累計 session 總費用
- **Prompt Caching**：固定內容放前面命中快取，可省 50-90% 的 prompt 處理費用
- **輕重模型分工**：次要任務（摘要、分類）用便宜的小模型，核心任務用貴的大模型

#### 安全檢查

**弱項：** AI 不能可靠地自我審查。讓它判斷自己的操作是否安全，等於球員兼裁判。

**對策：**
- **工具執行前攔截**：每次 AI 要用工具時，先過一層安全檢查，判斷這個操作是否安全
- **危險操作需確認**：刪除、發送、修改等不可逆操作，攔下來讓用戶確認
- **權限分級**：不同工具設不同權限等級，讀取類工具自動放行，寫入類工具需要額外驗證

#### 狀態注入

**弱項：** AI 在長對話中容易忘記自己的任務清單、計畫、限制。

**對策：**
- **每輪自動注入**：每次 call API 前，自動把當前的待辦事項、計畫、記憶等狀態資訊塞進 context
- **系統提醒**：在對話中插入系統級提醒，告訴 AI 當前的模式、限制、狀態（AI 看得到但用戶看不到）
- **記憶系統**：重要資訊持久化存檔，每輪自動載入相關記憶，確保 AI 不會忘記關鍵資訊

#### 自動恢復

**弱項：** AI 撞到錯誤時不會自救——context 爆了它不知道怎麼縮、輸出被截斷它不會繼續、API 失敗它不會重試。

**對策：**
- **Context 滿了**：自動觸發壓縮 → 移除圖片 → 摘要舊對話 → 重試
- **輸出被截斷**：偵測到截斷後自動注入「請繼續」指令，讓 AI 接著完成
- **API 失敗**：指數退避重試（等 1 秒 → 2 秒 → 4 秒），超過次數才放棄
- **連續失敗熔斷**：設定最大重試次數，連續失敗超過門檻就停下來，不要無限重試浪費錢

#### 為什麼簡單型和分流型不太需要擔心這些？

因為它們的流程是程式寫死的。程式控制流程意味著：context 大小可預測、每輪只做一件事、不會有 AI 失控的問題。自主型把控制權交給 AI，AI 可能跑 1 步就結束，也可能跑 50 步——這些弱項才全部浮現，需要外部程式幫忙管控。
