# Router Agent 知識庫

## 這個架構適用的場景

這是為**任務明確、意圖簡單**的 Agent 設計的架構。

這種架構的核心是用**意圖分析當路由器**，根據判斷結果把請求分派到對應的任務去執行，所以叫 Router Agent。當 Agent 的服務範圍明確（例如：幫用戶找講師、找課程），意圖類型有限且可預先定義時，適合用這種**管線式架構**——由設計者預先規劃好每一步的流程，系統按順序執行。

**與其他設計方式的差異：**

如果任務複雜、意圖多元（例如 Claude Code），沒辦法預先列舉所有意圖，就會採用不同的設計：一個大 prompt 加上工具定義，讓 AI 自己判斷該用什麼工具。流程由 AI 動態決定。

管線式架構的特點是：**流程可控、行為可預測、成本較低**。適合在任務範圍小的情境下使用。

## 基礎 Part 1 — Agent 架構與流程

整個 Agent 的運作流程如下：

```
用戶輸入 → 上下文工程 → 意圖分析 → 任務執行 → 上下文工程 → AI 回應
```

### 1. 用戶輸入

用戶發送訊息給 Agent。這是整個流程的起點。

### 2. 上下文工程（為意圖分析組裝資訊）

AI 不會自己知道之前聊了什麼，需要由系統把相關資訊組裝好再給它。

這一步的目的是幫 AI 做好意圖分析的準備。系統會組裝：
- 用戶的當前訊息
- 最近的對話紀錄（讓 AI 知道上下文）

為什麼上下文工程會出現兩次？因為意圖分析和回應生成需要的資訊不同，所以要分別組裝。意圖分析只需要輕量的上下文來判斷用戶要什麼；回應生成則需要完整的查詢結果來產出答案。

### 3. 意圖分析

AI 根據組裝好的上下文，判斷用戶的意圖並拆解任務。

因為這是管線式架構，意圖分類是預先定義好的（例如：找講師、找課程、超出範圍）。AI 的工作是把用戶訊息對應到這些分類，並提取查詢所需的參數。

### 4. 任務執行

根據意圖分析的結果，系統執行具體的查詢動作（例如查資料庫、搜尋向量資料庫）。

這一步是系統邏輯在運作，不是 AI。系統根據意圖分析拿到的分類和參數，去執行對應的查詢任務。

### 5. 上下文工程（為回應生成組裝資訊）

第二次上下文工程。這次要把所有資訊組裝好，讓 AI 能生成最終回應。

系統會組裝：
- 對話紀錄
- 用戶訊息
- 意圖分析結果
- 各項查詢結果
- AI 的行為指令（角色設定、回應規則等）

### 6. AI 回應生成

AI 根據組裝好的上下文，生成最終回應給用戶。

AI 只會根據你給的資訊來回應。給什麼、怎麼描述、告訴它怎麼用，決定了回應的品質。

## 進階 Part 2 — 模組知識庫

> 以下是各模組的進階知識點，按需查閱。這些是實作上的參考做法，不是必須遵守的規則。

### 意圖分析

- **意圖分類與信心度門檻**：為每個意圖預測設定信心度分數。例如 ≥0.8 明確執行，<0.8 則向用戶追問確認。門檻值依場景調整。
- **短字優化**：當用戶輸入字數少（例如 <10 字）時，優先判斷是否包含查詢目標；如果沒有，則回顧歷史對話來補充上下文。
- **代詞與指代處理**：用戶說「那個」、「她」時，需要回顧歷史對話找到指涉對象。例如用戶先問了某位講師，接著說「她的課程有哪些」，需從前文推斷「她」是誰。
- **模糊輸入容錯**：用戶可能打錯字或少打字（例如「陳雨」其實是「陳雨瑭」），結合上下文可推斷出正確的查詢對象。

### 任務執行

- **多策略並行查詢**：對同一個用戶請求，可同時觸發多種查詢策略。例如同時執行「姓名 SQL 模糊比對」、「專業領域向量搜尋」、「課程名稱 SQL 模糊比對」，再整合結果。
- **向量搜尋**：將文字轉成數字向量，計算語意距離。即使沒有共同關鍵字，語意相近的詞在向量空間中也會靠在一起。適合用在語意匹配的場景（例如搜尋專業領域）。
- **SQL 模糊比對**：適合用在有明確目標的精確查詢（例如講師姓名、課程名稱）。
- **輕量模型與重量模型分工**：查詢解析和篩選用輕量模型（快速、低成本），最終回應生成用重量模型（品質高）。將高成本模型限縮在最需要品質的環節，整體成本可降低約 80%。

### 記憶設計

- **對話紀錄（短期記憶）**：意圖分析階段和回應生成階段可以載入不同輪數的對話。例如意圖分析載入最近 10 輪（輕量判斷即可），回應生成載入最近 20 輪（需要更多上下文）。
- **工具記憶（短期記憶）**：記錄用戶每次執行的任務或使用的工具，只要知道上次做到哪裡即可，不需要翻遍整段對話。
- **長期記憶**：存取用戶偏好等跨對話的資訊。但記憶不是越多越好，過多記憶會增加上下文的複雜度與 AI 出錯的可能性。功能單純的 Agent 不一定需要啟用。
- **事件記錄模式**：用事件（open / complete / reanalyze）記錄用戶的每次操作，而非覆蓋更新狀態欄位。這樣能保留完整的操作軌跡，方便回溯分析用戶行為。
- **visible_to_user 機制**：所有操作都完整記錄供 AI 分析使用，但用戶介面只顯示已完成（complete）的結果。做到完整記錄與乾淨介面並存。
- **記憶隔離**：當系統有多個 Agent 時，各 Agent 的記憶要隔離，避免角色混淆（例如分析 Agent 的專業對話不該影響銷售 Agent 的語調）。跨 Agent 協作時只傳遞結果摘要，不共享完整對話。

### 上下文工程

- **劇本組合**：給 AI 的上下文需要有結構地組合，包含對話紀錄、用戶訊息、任務分析結果、各項查詢結果。重點不是把所有東西塞進去，而是「組合什麼資訊」、「怎麼描述這些資訊」、「告訴 AI 怎麼用」。
- **指令設計**：包含角色設定、核心職責（Dos）、行為限制（Don'ts）、回應策略（延續討論或新查詢）、處理原則（查無結果時怎麼回應）。
- **Compose 函數的取捨邏輯**：系統內部傳遞完整查詢資料，但組裝給 AI 的文字只取部分欄位。完整保留是為了未來擴展，精簡是為了控制上下文品質、避免無關資訊干擾 AI 判斷。
- **給 AI 的文字格式化**：查詢結果要用結構化格式（標題、列點、分段）呈現給 AI，而不是丟一坨 raw data。AI 對結構化文字的理解與回應品質明顯更好。
