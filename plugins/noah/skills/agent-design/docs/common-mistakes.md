# 常見誤區與失敗案例

> 以下是 Agent 設計中最常踩的坑。每個案例都來自實務經驗，幫你避開別人走過的彎路。

---

## 1. 過度設計——用大砲打蚊子

**情境**：PM 想做一個自動回覆退貨政策的機器人，直接選了自主型架構，給 AI 十幾個工具。

**結果**：成本是簡單型的 30 倍，但回答品質差不多。因為退貨政策就那幾條，固定流程就能處理。

**教訓**：先問「最簡單的架構能不能解決？」。如果答案是「能」，就不要升級。

---

## 2. RAG 濫用——塞太多無關資料

**情境**：為了讓 AI「什麼都能答」，把整個公司的文件庫全部灌進 RAG。

**結果**：用戶問「怎麼退貨」，AI 撈到了退貨政策、員工手冊裡的報銷流程、還有一份三年前的內部備忘錄。回答又長又偏。

**教訓**：RAG 不是越多越好。只放用戶真的會問到的資料，設定相關性門檻過濾無關結果。寧可少撈、撈準，也不要多撈、撈雜。

---

## 3. 沒有退場機制——AI 硬撐到底

**情境**：沒有設計「查無結果」或「不確定」的處理流程。

**結果**：AI 找不到答案時，自己編造了一個看起來合理但完全錯誤的回答（幻覺）。用戶信以為真，造成客訴。

**教訓**：一定要在 prompt 裡明確告訴 AI：「查不到就說查不到，不確定就說不確定」。並設計 fallback 轉人工的機制。AI 說「我不知道」永遠比說錯好。

---

## 4. 忽略成本——Token 用量失控

**情境**：自主型 Agent 上線後，發現某些用戶的對話會觸發 AI 連續呼叫工具 30-40 次。

**結果**：單次對話成本飆到 $2-5，月帳單爆炸。

**教訓**：自主型一定要設定每次對話的最大工具呼叫次數（例如上限 15 次）和最大 token 消耗量。超過就停下來告訴用戶，不要無限跑下去。上線前先用壓力測試估算最壞情況的成本。

---

## 5. 記憶設計過度——記太多反而出錯

**情境**：為了「個人化體驗」，Agent 記住了用戶的所有歷史偏好和操作紀錄，每次對話都全部載入。

**結果**：上下文太長，AI 被大量歷史資訊干擾，反而答非所問。而且舊的偏好可能已經過時，導致推薦不準確。

**教訓**：記憶不是越多越好。短期記憶保留最近 5-10 輪就夠，長期記憶只存真正重要的偏好，並定期清理過時資訊。

---

## 6. 沒做安全檢查——AI 隨意執行操作

**情境**：自主型 Agent 有「刪除訂單」的工具，沒有加確認機制。

**結果**：用戶隨口說「把這個取消掉」，AI 直接刪了訂單，沒有任何確認。

**教訓**：所有寫入、刪除、發送類的操作，必須在執行前讓用戶確認。讀取類可以自動放行，但修改類一定要攔截。這不是「建議」，是「必須」。
