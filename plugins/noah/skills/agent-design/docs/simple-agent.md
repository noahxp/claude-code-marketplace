# Simple Agent 知識庫

## 這個架構適用的場景

這是為**單一任務、固定流程**的 Agent 設計的架構。

典型的例子是簡單客服對話機器人：用戶問問題，系統撈資料，AI 根據資料回答。每次都走一樣的路，沒有分岔。不需要判斷用戶意圖、不需要路由分派、不需要讓 AI 自己決定用什麼工具。

**與其他類型的差異：**

- 跟**分流型**的差異：分流型需要先做意圖分析，再根據意圖走不同路線。簡單型不需要，因為只有一條路。
- 跟**自主型**的差異：自主型讓 AI 自己決定要用什麼工具和步驟（tool use）。簡單型的流程是開發者寫死的，AI 只負責最後一步——回應。

簡單型的特點是：**流程固定、行為可預測、成本最低**。適合任務單純、不需要複雜判斷的場景。

## 基礎 Part 1 — Agent 架構與流程

整個 Agent 的運作流程如下：

```
用戶輸入 → 資料檢索 → 上下文工程 → AI 回應
```

### 1. 用戶輸入

用戶發送訊息給 Agent。這是整個流程的起點。

### 2. 資料檢索

系統根據用戶的訊息，自動去撈相關資料。這一步是程式在做，不是 AI。

常見的檢索方式：
- **SQL 查詢**：從資料庫撈結構化資料（例如查訂單、查會員資料）
- **RAG（向量搜尋）**：從知識庫搜語意相關的內容（例如搜 FAQ、搜產品說明）

兩者可以只用一種，也可以同時用，看需求。

### 3. 上下文工程

把所有資訊組裝成一包，準備送給 AI。AI 不會自己知道任何事，你給什麼它就看什麼。

系統會組裝：
- **System Prompt**：角色設定（你是誰）、行為規範（該做什麼、不該做什麼）
- **對話紀錄**：最近幾輪的對話，讓 AI 知道上下文
- **檢索結果**：上一步撈到的資料
- **用戶訊息**：用戶這次說的話

組裝的順序和格式會影響 AI 回應的品質。重點不是把所有東西塞進去，而是組裝什麼、怎麼描述、告訴 AI 怎麼用。

### 4. AI 回應

AI 根據你組裝好的上下文，生成回應給用戶。

它只會根據你給的資訊來回答。給什麼、怎麼描述、告訴它怎麼用，決定了回應的品質。

## 進階 Part 2 — 模組知識庫

> 以下是各模組的進階知識點，按需查閱。這些是實作上的參考做法，不是必須遵守的規則。

### 資料檢索

- **SQL vs RAG 的選擇**：目標明確、有精確欄位可查的用 SQL（例如「訂單編號 A123 的狀態」）；目標模糊、需要語意匹配的用 RAG（例如「怎麼退貨」）。兩者不衝突，可以並用。
- **RAG 的基本原理**：把文件切成小段，每段轉成數字向量存起來。用戶問問題時，把問題也轉成向量，找出距離最近的幾段文字，當作檢索結果塞進 prompt。
- **檢索結果篩選**：不是撈到的全部都塞給 AI。設定相關性門檻，只給夠相關的結果，避免無關資訊干擾 AI 判斷。
- **查無結果的處理**：如果什麼都撈不到，不要硬塞空結果。在 prompt 裡告訴 AI「沒有找到相關資料」，讓它用預設的回應策略處理（例如「抱歉，我目前無法查到相關資訊，建議您聯繫客服人員」）。

### 上下文工程

- **System Prompt 結構**：建議分成幾個區塊——角色設定（你是 XX 公司的客服助手）、核心職責（回答用戶關於 XX 的問題）、行為規範（Dos & Don'ts）、回應風格（語氣、長度、格式）。
- **檢索結果的格式化**：查詢結果要用結構化格式（標題、列點、分段）呈現給 AI，不要丟一坨 raw data。AI 對結構化文字的理解與回應品質明顯更好。
- **告訴 AI 怎麼用資料**：不只是塞資料，還要告訴 AI「以下是查詢結果，請根據這些資料回答用戶的問題，不要編造資料裡沒有的內容」。明確的指令能減少 AI 幻覺。
- **控制回應行為**：在 prompt 裡設定清楚的規則，例如：查到資料就根據資料回答、查不到就引導用戶聯繫人工客服、不確定就說不確定，不要猜。

### 記憶設計

- **對話紀錄（短期記憶）**：保留最近 N 輪對話，讓 AI 知道前面聊了什麼。N 的大小依場景決定，一般 5-10 輪就夠。太多會增加成本和雜訊，太少會讓 AI 失去上下文。
- **不一定需要長期記憶**：簡單客服機器人的對話通常是一次性的（問完就走），不太需要跨對話記住用戶偏好。如果有需要，可以加，但不是必須的。
- **對話紀錄的格式**：存的時候區分角色（user / assistant），載入時按時間順序排列，讓 AI 能清楚分辨誰說了什麼。
