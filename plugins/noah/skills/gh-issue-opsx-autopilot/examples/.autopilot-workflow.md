# Autopilot Workflow — mis-rms

> 本檔案為 gh-issue-opsx-autopilot Skill 的專案 Workflow 定義檔，須搭配該 Skill 使用。

## Issue 前置檢查

- 標記為 `discussion` 的 Issue **禁止進入開發流程**，須中止並回報
- Issue 標題為純描述格式，不含 `feat:`、`fix:` 等前綴（分類由 Labels 承擔）

## Naming

- Issue 編號補零至三碼：`NNN`（如 Issue #5 → `005`）
- 功能英文名稱：從 title 提取，kebab-case，最多三個單字
- 分支名：`feature/NNN-kebab-name`
- Spec 路徑：`sa/spec/NNN-kebab-name/`
- 實作工作流 change 名：由 `/opsx:propose` 自動決定，命名慣例為 kebab-case + NNN 編號後綴（如 `filter-options-null-023`）

## Branch Strategy

從 `dev` 分支建立，使用 `gh issue develop` 關聯 Issue：

```bash
git checkout dev && git pull
gh issue develop $ARGUMENTS --base dev --name feature/NNN-kebab-name --checkout
```

## Commit Convention

```bash
git add <相關檔案>
git commit -m "$(cat <<'EOF'
<type>: <繁體中文描述> (#NNN)

<Why — 說明變更動機與背景>

Refs #NNN
EOF
)"
```

- **type**：執行 `git diff --cached` 判斷變更內容，據此選擇適當的 Conventional Commits type（`feat:` / `fix:` / `refactor:` / `docs:` / `perf:` / `test:` / `style:` / `chore:` 等）
- **Subject**（What）：繁體中文描述，結尾附 `(#NNN)`
- **Body**（Why）：說明「為什麼」需要這個變更——問題的背景、動機、與變更前行為的對比。不要重複 diff 已能看到的內容
- **Footer**：中間 commit 使用 `Refs #NNN`，最終 commit 使用 `Closes #NNN`
- Subject、Body、Footer 之間各隔一行空行
- 若有「額外修正（既有問題）」，以獨立 commit 提交

## Spec Reference

查找規格文件的優先順序：

1. **首查 `openspec/specs/`** — 已歸檔的實作技術規格（Single Source of Truth）
2. **次查 `sa/spec/`** — 尚未歸檔的功能，或需理解需求背景時參考

涉及跨模組修改時，交叉查閱相關模組的 `openspec/specs/` 與 `sa/spec/`，確認角色權限與狀態流轉規則。

## Spec Authoring

產出路徑：`sa/spec/NNN-kebab-name/spec.md`

必要章節：

1. **業務背景** — 問題源起與商業價值
2. **規格書依據** — 引用的既有規格文件
3. **現狀分析** — 目前程式碼的行為與問題
4. **修正規格** — 具體的修正內容與預期行為
5. **影響範圍** — 受影響的檔案、模組、API
6. **測試規格** — 需要驗證的測試案例

## Implementation

使用 **OpenSpec 工作流**，分四步驟執行：

### Step 1: Propose

調用 `opsx:propose`，參數為以下描述：
「<從 SA spec 整理的 change 描述，含 Issue 編號、變更內容、影響範圍>」
Change name 為 `<change-name>`。
SA spec 位於 `sa/spec/NNN-xxx/spec.md`。

Agent 完成後，讀取回傳結果確認 artifacts 已建立。

**Commit**：將 SA spec 與 OpenSpec propose 產物提交（需求分析產物）。

### Step 2: Apply

調用 `opsx:apply`，參數為 change name `<change-name>`。
遵循 TDD 流程（Red → Green → Refactor）實作所有 tasks。
後端必須撰寫測試（單元 + 整合），前端不撰寫測試。

Agent 完成後，讀取回傳結果確認所有 tasks 已完成。

### Step 3: Verify

調用 `opsx:verify`，參數為 change name `<change-name>`。
驗證三個維度：Completeness、Correctness、Coherence。
回傳驗證報告。

若回傳結果包含 CRITICAL issues → 在主流程中修復，再次用 Agent 執行 verify，直到全部通過。

**Commit**：將 apply 實作的所有程式碼變更提交（實作產物）。

### 重入偵測補充

| 偵測條件 | 接續點 |
|---------|--------|
| 有 branch + spec，但無 `openspec/changes/` 下的 change | → Spec 審查 |
| 有 change 但 tasks 未全部完成 | → Apply（接續未完成 tasks） |
| 有 change 且 tasks 全部完成 | → Verify |

### Commit Points

實作階段依以下時間點提交 commit：

| 時間點 | 內容 | 說明 |
|--------|------|------|
| Propose 完成後 | 需求分析產物 | SA spec + OpenSpec propose artifacts |
| Apply + Verify 完成後 | 實作產物 | 程式碼變更（與後續審查修正分開） |
| Code Review 修正後 | 審查修正 | Review 與 Simplify 的修正（若無修正則跳過） |
| E2E + Archive 完成後 | 最終提交 | E2E 測試、歸檔等收尾產物，Footer 使用 `Closes #NNN` |

以上 commit 時間點由 SKILL 主流程統一執行，Implementation 步驟中的 `**Commit**` 標記僅為時間點指示。

## Review

審查工具：
- `pr-review-toolkit:code-reviewer` — 程式碼品質、邏輯錯誤、安全漏洞
- `pr-review-toolkit:pr-test-analyzer` — 測試覆蓋率與測試品質
- `pr-review-toolkit:silent-failure-hunter` — 靜默失敗與錯誤處理

規格參考：`sa/spec/NNN-xxx/spec.md` 與 Phase 2 產出的 OpenSpec change 目錄。

### 既有問題分流

審查時發現的「既有程式碼問題」（非本次變更引入），依以下流程處理：

**分流判定流程**：

對每一項既有問題，依序執行：

1. **Issue 列管檢查**（Issue 留言去重子程序）— 已有 Issue 追蹤的項目直接跳過
2. **SA Spec 影響度判定** — 讀取 `sa/spec/NNN-xxx/spec.md`，比對該問題的修正是否會改變 spec 定義的需求規格（含業務邏輯、API 契約、資料模型等）
3. 分流：

| 判斷條件 | 處理方式 |
|---------|---------|
| **不需討論**：修正方式明確、風險低、不涉及架構決策（如：缺少 try-catch、空 catch block） | 直接修正，與主要變更合併 commit |
| **可直接修正**：雖涉及較大變更，但確認 (1) 不影響 spec 定義的需求規格，且 (2) 無其他 GH Issue 列管 | 直接修正，以**獨立 commit** 提交，並列入 PR body「額外修正」區塊 |
| **需要討論**：修正會改變 spec 定義的需求規格、需求不明確、或影響範圍無法自行判定 | 在 GH Issue 上留言通知 assignees 與 author |

## Testing

1. 撰寫 `sa/spec/NNN-kebab-name/e2e.md`（E2E 測試腳本）
2. 啟動開發伺服器：
   - 後端：`gradle bootRun`（或專案對應指令）
   - 前端：`npm run dev`（Vite）
3. 測試方式：
   - 若有 Chrome DevTools MCP → 使用瀏覽器自動化執行 UI 測試
   - 若無 → 透過 API 直接呼叫 + 原始碼確認驗證，並在 `e2e.md` 註明驗證方式
4. 將測試結果記錄回 `e2e.md`

## Guardrails

- 所有程式碼變更遵循 TDD（Red → Green → Refactor）
- 後端必須撰寫測試（單元 + 整合），前端不撰寫測試
- 繁體中文：程式碼註解、文件、Git commit（Conventional Commits）
- 禁止硬編碼密鑰
- 修改權限相關程式碼前，先分析現有安全模式（參考 CLAUDE.md §權限系統）
