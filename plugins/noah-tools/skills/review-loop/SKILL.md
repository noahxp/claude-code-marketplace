# Review Loop

對目前分支反覆審查、複查、修正，直到 medium 審查清零、且獨立判定不需再審一輪，再收尾並回報。遇到要使用者決定的項目就停下來問，問完才修：使用者的決定可能改變同一批其他項目的修法。

```
/noah-tools:review-loop [base]
```

`base` 預設為 origin 的預設分支（`git symbolic-ref --short refs/remotes/origin/HEAD` 去掉 `origin/`）。

## 名詞

- **帳本**：本分支所有審查項目的判定紀錄，跨審查、跨 `/clear` 保留，用來略過已判定過的項目。格式見〈帳本〉。
- **盲審**：複查的 subagent 只拿到審查項目本身，看不到你的判定。
- **紅燈**：照項目描述寫的測試在修正前失敗，且失敗原因與描述相符。
- **清零**：一次 medium 審查的新項目全部驗證完，沒有任何一項的處置是「要修」。

## 流程

```
0 開始
1 xhigh      有要修 → 修正 → 2；沒有 → 4（兩軸已跑過則 5）
2 medium     有要修 → 修正 → 再跑 2；清零 → 3
3 再審判定   要 → 下一輪的 1；不用 → 4（兩軸已跑過則 5）
4 兩軸審查   有要修 → 修正 → 2；沒有 → 5
5 同步與驗證
6 回報
```

上限：外圈最多 3 輪，每輪 medium 最多 3 次。碰到上限即**未清零**：已驗證成立的那批照常修完並 commit，接著跳到第 6 步，第 5 步留給使用者決定。

### 0. 開始

1. `git status --porcelain` 須為空；有未提交的改動就停下回報。迴圈每修一批就 commit，未提交的改動會混進修正 commit。
2. 決定 base，確認 `git diff <base>...HEAD` 非空。
3. 讀 `<skill base directory>/../../agents/finding-verifier.md` 的〈判定〉與〈證據〉，你自己判定時套用同一套標準。
4. 開啟或建立帳本，追加本次執行的「執行」行。輪次 n = 1。

完成條件：工作區乾淨、base 已確定、帳本已記下本次執行。

### 1. xhigh（第 n 輪）

1. 在帳本狀態行記下本輪起點 = `HEAD`，medium 次數 = 0。
2. 依〈呼叫審查〉跑 xhigh，等它完成。
3. 依〈驗證一批項目〉處理回報的全部項目。
4. 有要修 → 依〈修正一批項目〉修正，進第 2 步。沒有 → 進第 4 步（兩軸已跑過則第 5 步）。

完成條件：這次回報的每一項在帳本都有定案與處置。

### 2. medium

1. medium 次數加 1，依〈呼叫審查〉跑 medium，等它完成。
2. 依〈驗證一批項目〉處理。
3. 有要修 → 依〈修正一批項目〉修正；medium 次數未滿 3 就重跑本步，滿 3 即未清零。沒有 → 清零，進第 3 步。

完成條件：清零，或碰到上限。

### 3. 再審判定

派 `noah-tools:rereview-judge`，派工訊息給 repo 絕對路徑（`git rev-parse --show-toplevel`）、base、本輪起點、帳本路徑。把它的結論與成立的判準寫進帳本狀態行。

- 要再審：n < 3 → n 加 1，回第 1 步；n = 3 → 未清零。
- 不用：兩軸未跑 → 第 4 步；已跑 → 第 5 步。

### 4. 兩軸審查

每次執行只跑一次。

1. 依〈呼叫審查〉跑兩軸審查，在帳本狀態行記下兩軸已跑。
2. 依〈驗證一批項目〉處理。
3. 有要修 → 依〈修正一批項目〉修正，回第 2 步；這批修正併入當前輪次，medium 次數歸零。沒有 → 第 5 步。

### 5. 同步與驗證

1. 依專案 CLAUDE.md，把這次迴圈的修正一次同步到設計紀錄（spec 副本、issue、ADR 等），並 commit。
2. 跑全套測試與改動檔案的 lint，保留輸出原文給報告。
3. 分支有 upstream 就 push。有 PR 的話，把 PR 描述中測試結果或驗證的段落換成這次的輸出，其餘段落維持原樣。

完成條件：測試與 lint 綠燈、已 push、PR 描述的測試段落對應目前的 `HEAD`。

### 6. 回報

依〈報告〉輸出。回報後使用者要求改程式時，從〈修正一批項目〉接續，再回第 2 步（medium 次數歸零），帳本照用。

## 呼叫審查

| 審查 | 呼叫 | 回傳 |
|---|---|---|
| xhigh、medium | Skill `code-review`，args 為 `<等級> <目前的本機分支名>` | 在背景執行，完成時以通知回傳；結尾的 JSON 陣列就是審查項目 |
| 兩軸 | Skill `mattpocock-skills:code-review`，args 為 `<base>` | 在本 session 執行，回傳 Standards 與 Spec 兩份報告 |

- target 一律給本機分支名。不給 target 時它審 `@{upstream}...HEAD`，分支 push 過後只剩未 push 的 commit；給 PR 編號時它讀 `gh pr diff`，看不到本機的修正 commit。
- `code-review` 審的是工作區，等它完成之前工作區維持不動。
- 兩軸的 Standards 報告中，Fowler code smell 一類的判斷題歸整潔；違反專案明文規範的硬性違規，以及 Spec 的項目，都是事實主張。

## 驗證一批項目

輸入是一次審查回報的全部項目。

1. **比對帳本**：同一位置（同一函式）、同一錯誤機制的項目，就是帳本已有的那筆。`git diff <該筆錨點> HEAD -- <檔案>` 改到那個函式，或錨點已不存在時，該筆失效，當成新項目；否則略過。
2. **分類**：不造成錯誤結果的項目（重複程式碼、命名、效率等）歸整潔，直接寫入帳本，不複查。其餘是事實主張。
3. **派盲審**：每個事實主張派一個 `noah-tools:finding-verifier`，全部在同一則訊息裡派出。派工訊息只放 repo 絕對路徑、base、該項的 `file`、`line`、`summary`、`failure_scenario` 原文，以及專案 CLAUDE.md 指向的 spec、ADR、術語表位置。
4. **自己判定**：複查進行時，逐項做出判定並附證據，先寫進帳本，再看複查結果。
5. **比對**：兩方判定相同即定案。不同時，照 `failure_scenario` 的前提與預期結果寫測試並執行：紅燈 → 成立；通過 → 誤報（測試不 commit，測試名與結果記入帳本）；寫不出測試 → 未能證實。
6. **處置**：依〈處置〉決定，錨點記為目前的 `HEAD`。
7. **詢問**：有待決定的項目，依〈詢問〉停下來問，依答覆改成最終處置。

完成條件：每一項都有最終處置，沒有留下待決定；定案為成立或誤報的項目，帳本裡都有兩方的證據。

## 修正一批項目

1. 先為這批每個要修的項目寫測試（可從複查回傳的測試草稿改起）並執行，須為紅燈。沒有紅燈，或紅的原因與描述不同，該項降為未能證實、處置改為待決定，在動手修正之前依〈詢問〉問完。例外：併發序列無法以測試穩定重現時，兩方都給了完整的 `file:line` 序列即可修，修正仍要附測試釘住修正後的行為。
2. 修正。與要修項目在同一處的整潔項目可一併修。
3. 依專案 CLAUDE.md 跑全套測試與改動檔案的 lint，須綠燈。測試一律在本 session 逐一執行。
4. 依專案的 commit 慣例在本機 commit，把 commit sha 記到各項目的處置。

完成條件：每個要修的項目都已修並記下 commit，或已降級並依答覆處置；測試與 lint 綠燈。

## 處置

| 處置 | 條件 | 觸發 medium |
|---|---|---|
| 要修 | 成立，且修正不改變 spec 寫明的行為 | 是 |
| 待決定 | 成立，但修正會改變 spec 寫明的行為、要接受殘餘風險，或超出 spec；以及不屬於上線驗收的未能證實 | 依〈詢問〉的答覆 |
| 上線驗收 | 未能證實，且要靠真實環境（叢集、外部服務）才能確認 | 否 |
| 不修 | 誤報 | 否 |
| 整潔 | 不造成錯誤結果；同批有要修時一併修，否則列入報告 | 否 |

## 詢問

用 AskUserQuestion，一個待決定項目一題，一次最多 4 題，超過就分次問。使用者只看得到問題視窗，每題要自足：項目編號、一句主張、兩方的判定與證據摘要，以及需要使用者決定的原因（會改變 spec 的哪條行為、要接受什麼殘餘風險、超出 spec 的哪部分，或卡在哪個前提）。

選項從下表挑該項適用的，你建議的放第一個，標籤加「(建議)」：

| 選項 | 之後的處置 |
|---|---|
| 修正 | 要修，併入這批修正 |
| 接受並記入 ADR | 記入帳本，第 5 步同步時寫進 ADR |
| 另開 issue | 依專案 CLAUDE.md 的 issue 慣例立即開立，編號記入帳本 |
| 不處理 | 記入帳本 |

使用者選「其他」時照所給的指示做，並記入帳本。答覆會影響同一批其他項目的修法時，先依答覆調整那些項目，再進〈修正一批項目〉。

## 帳本

路徑：`$(git rev-parse --git-dir)/review-loop/<分支名，/ 換成 ->.md`。在 worktree 中 `--git-dir` 是各自的目錄，不進版控。

```markdown
# review-loop 帳本：feature/x

- base：main
- 執行：2026-11-04 16:02，起點 828acfb0
- 狀態：第 2 輪｜medium 1 次｜本輪起點 a3326c14｜兩軸未跑｜再審判定：要（判準 1）

## R1-X3
- 來源：xhigh，第 1 輪
- 位置：backend/app/workers/build_task.py:2074 `_redeploy`
- 主張：<summary>；序列：<failure_scenario 摘要>
- 主 session：成立｜<證據>
- 複查：成立｜<證據>
- 定案：成立
- 處置：要修，已修 fc968a9d
- 決定：<使用者的答覆>（問過的項目才有）
- 錨點：828acfb0
```

- 編號為 `R<輪>-<來源><序號>`，來源 X = xhigh、M = medium、S = Standards、P = Spec，序號在同一輪的同一來源內連續。
- 每次執行追加一行「執行」；狀態行隨進度覆寫，`/clear` 或 context 摘要後依它接續。

## 報告

```markdown
## review-loop：清零｜未清零（碰到的上限）

| 輪 | 審查 | 新項目 | 要修 | commit |
|---|---|---|---|---|

### 問過的項目
- R1-X2 <一句主張> — 決定：<使用者的答覆>；結果：<commit、ADR 或 issue 編號>

### 上線驗收
### 不修（誤報）
- R1-X9 <主張> — <不成立的前提>
### 未修的整潔項目
### 驗證
<測試與 lint 輸出的結尾原文>；push 與 PR 描述的狀態
```

沒有內容的段落寫「無」。
